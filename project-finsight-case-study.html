FinSight AI

An AI-native financial intelligence platform that turns transactions, loans and company cash flow into calibrated predictions and evidence-backed explanations. The backend keeps the money, the models keep the uncertainty, and a human keeps the decision.

The problem

Most fintech stops at the ledger

What breaks trust

  • Fraud engines are rule bundles: opaque, brittle, uncalibrated and easy to game.
  • Credit is either a black-box score or a spreadsheet with no reason codes.
  • Cash-flow views are historical and say nothing about what is coming.
  • LLM chat over financial data is fluent and wrong, because the model computes numbers instead of reading them.

The contract

The backend calculates. ML predicts. AI explains. Humans decide. Every prediction carries a calibrated score, contributors, limitations and provenance. Every model has a deterministic fallback. No model writes a balance, changes a status, approves a loan or closes a case.

What I built

The parts that make the numbers hold

A feature platform

Point-in-time features, explicit forbidden lists, assert_no_leakage at build time, leakage tests in CI, and a parity test proving one-row scoring matches the batch path.

Fraud, calibrated

XGBoost with native imbalance weights, isotonic calibration on validation and a cost threshold (FN=10, FP=1), checked over three stratified splits.

Credit that explains itself

Additive WOE scorecard, so every decline has exact reason codes. The LightGBM challenger lost out of time, so the interpretable model stayed.

Honest intervals

Quantile LightGBM with split-conformal widening and a conservative risk path for low-balance alerts. Recorded facts are labelled apart from assumptions.

An LLM that reads, never computes

Four levels from explainer to what-if. Tool-only access, numeric fidelity checks, an evidence scope per answer, injection defence and a deterministic fallback.

FinSight Business

Company workspace as a modular monolith: roles, departments, invoices, bills, payments, expenses with separation of duties, budgets, projects and audit events.

Case study inside the case study

The fraud model that stayed in shadow

The first fraud model beat the rule engine on every secondary metric: PR-AUC 0.197 vs 0.133, ROC-AUC 0.901, ECE 0.0025 vs 0.0766, cost 5,803 vs 6,408. But the programme had committed to +0.10 PR-AUC before looking at the test. It delivered +0.064, so it stayed in shadow.

That forced an honest next iteration. The labels were the ceiling, not the model family; two fraud families were invisible at the top 1%; device and balance features were defective; and the consumed test needed a fresh protocol. The answer was a benchmark-first rewrite on real public data, with repeated splits, calibration, cost thresholds and bootstrap intervals. The model did not get bigger. The evaluation got better.

Principles and stack

What I would defend in a review

Principles

  • Split before fitting: temporal, vintage or grouped.
  • Test once; a consumed test is archived.
  • Calibration is a gate, not a plot.
  • Cost is a business input to the threshold.
  • Measure selection bias: 0.020 AUC, quantified.
  • Shadow before assist; fallback always; provenance in every response.

Stack

  • ML: Python 3.11, scikit-learn, XGBoost, LightGBM, pandas, statsmodels, FastAPI.
  • Backend: Java 25, Spring Boot 4, JPA, Flyway, PostgreSQL 17, Spring Security/JWT, OpenAPI.
  • LLM: OpenAI-compatible provider (Groq), tool-calling, prompt registry, numeric validation.
  • Ops: pytest, model registry, dataset manifests, sha256 artifact provenance, Docker-ready.
